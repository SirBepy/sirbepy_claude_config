# /commit's version bump never touches src-tauri/Cargo.toml, so Rust crate versions drift

**Type:** skill-improvement
**Origin:** ai

## Goal

Make `/commit v` / `pushbump` / `pushnbump` bump a Tauri project's Rust crate version alongside the
JSON manifests, so the crate version stops silently falling behind the app version.

## Context

Found 2026-08-12 in `C:\Users\tecno\Desktop\Projects\windows_taskbar_widgets` while investigating an
unrelated logging bug. That repo's versions had drifted six patch releases apart:

- `package.json` - `0.1.10`
- `src-tauri/tauri.conf.json` - `0.1.10`
- `src-tauri/Cargo.toml` - `0.1.4`
- `src-tauri/Cargo.lock` - `0.1.4` (follows Cargo.toml)

The cause is the bump procedure in `~/.claude/skills/commit/SKILL.md`, under `/commit v` / `bump`:

> 2. Find any other `.json` files in the **repo root** that contain a top-level `"version"` field

`Cargo.toml` misses on both criteria - it is TOML, not JSON, and it lives in `src-tauri/`, not the
repo root. So it has never been bumped in that project's history, and the same will be true of every
Tauri project this skill is used on.

Why it costs real time rather than being cosmetic: `env!("CARGO_PKG_VERSION")` is what a Rust app
logs as its own version. A session reading `app started; version=0.1.4` in a log while the installed
build is 0.1.10 will conclude it is looking at a stale log or a stale checkout, and re-derive its
analysis. That is exactly what happened in the session that found this.

## Approach

Amend the version-bump procedure in `~/.claude/skills/commit/SKILL.md` (the numbered list under
`/commit v` / `bump`, which `pushbump` and `pushnbump` both inherit):

1. Keep `package.json` as the source of truth.
2. Widen step 2 from "other `.json` files in the repo root" to also cover a Rust crate manifest when
   one exists: if `src-tauri/Cargo.toml` (or any `Cargo.toml` whose `[package]` name matches the
   project) has a `version = "..."` line under `[package]`, rewrite it to the new version.
3. After rewriting `Cargo.toml`, `Cargo.lock` must be regenerated by cargo, never hand-edited - run
   `cargo check` (or `cargo update -p <crate> --precise <new-version>` if a full check is too slow)
   from the crate dir, and include the resulting `Cargo.lock` in the commit pathspec.
4. Include both files in the pathspec alongside the JSON manifests.

Rejected alternative, worth recording so it is not re-litigated: having the skill scan every
`Cargo.toml` in the tree. Workspaces and vendored submodules (`vendor/tauri_kit` in the project where
this was found) contain crates that must NOT be bumped with the app. Scope it to the app crate only.

Check whether `/commit onlyv` / `onlybump` need the same widening - they share the procedure by
reference, so amending the one list should cover them, but confirm the wording does.

## Acceptance

- A `/commit pushnbump` in a Tauri project leaves `package.json`, `tauri.conf.json` and
  `src-tauri/Cargo.toml` all on the same version, with `Cargo.lock` updated by cargo.
- A non-Rust project is unaffected - the new step is a no-op when no crate manifest exists.
- Vendored/submodule crates are never bumped.
- The `VERSION: <new-version>` commit message shape from `pushnbump` step 4 is unchanged.
