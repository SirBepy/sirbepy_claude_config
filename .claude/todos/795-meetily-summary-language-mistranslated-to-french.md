# Meetily's AI meeting summary generated in French for a Croatian/English meeting

**Type:** task
**Origin:** ai

## Goal

Fix Meetily's meeting-summary language auto-detect so a Croatian/English meeting doesn't get
its AI-generated summary written in a third language (observed: French).

## Context

This is NOT about the `~/.claude` repo - it targets Joe's personal local-transcription tooling
at `C:\Users\tecno\tools\meetily-diarize\` (not a git repo, so it has no `.claude/todos/` of its
own; filed here as the only available backlog from that session).

Session built a diarization + English/Croatian transcript-language whitelist for Meetily
(`C:\Users\tecno\tools\meetily-diarize\diarize.py` + `langfix.py`) after Meetily's own Parakeet
ASR mistagged transcript segments into random languages (Cyrillic, Spanish, Portuguese). That
fix works and is verified (0 mistagged segments across an 83-segment, 32-minute real meeting).

Separately, Joe noticed Meetily's AI-generated meeting **summary** (not the transcript) came out
in French. Checked `metadata.json` for that meeting:
`C:\Users\tecno\Music\meetily-recordings\Meeting 2026-08-24_15-51-59_2026-08-24_13-51\metadata.json`
literally has `"detected_summary_language": "fr"`. The summary is generated by a local LLM
(qwen3.5:4b via Ollama, Meetily's "builtin-ai" provider, per its `settings` sqlite table) - a
completely separate subsystem from the Whisper/Parakeet transcription pipeline, so the transcript
whitelist fix does not touch it.

Researched whether Meetily has a setting to pin summary language: it does not. A user already
filed it as a feature request - github.com/Zackriya-Solutions/meetily issue #413 ("Change summary
output language"), open/unshipped as of 2026-08-26.

Claude offered Joe two remediation paths and Joe never picked one before running `/close`
("good enough i guess") - this is Claude's own unexecuted offer, not a dev-requested plan.

## Approach

Two options were offered, neither built yet:

1. **Check for a "regenerate summary" action** in Meetily's Summary tab/UI on that specific
   meeting - if it exists, regenerating might just re-roll the language guess correctly (untested,
   cheap to try first).
2. **Build a custom summary step onto the existing tool**, reusing the now-corrected
   `diarized_transcript.md`/`.json` output, feeding it to a local LLM (Ollama, same qwen3.5:4b
   already installed for Meetily) with an explicit language instruction (English or Croatian, not
   auto-detect) - mirrors the `langfix.py` pattern already built this session. Real new scope:
   needs its own design pass (trigger point - part of `diarize_meeting()` or separate script;
   output location - alongside `diarized_transcript.md` or written back to
   `meeting_notes.notes_markdown` in Meetily's sqlite).

## Acceptance

- Joe has a way to reliably get an English or Croatian meeting summary (not a third language) for
  meetings this tool already processes.
- Whichever path is taken, verified against a real recorded meeting the way the transcript
  whitelist was (not just "should work").
